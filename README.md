# Agentic URL Shortener System

A URL shortener service built and evolved by a real agentic orchestration
engine, demonstrating end-to-end SDLC automation with controlled autonomy.
This is a Java 21 / Spring Boot 3 project.

- **Product:** `urlshortener` — Spring Boot + SQLite URL shortener with
  create/redirect/analytics/delete APIs, rate limiting, and collision-safe
  code generation.
- **Engine:** `orchestrator` — a domain-agnostic workflow engine with
  an explicit DAG, entry/exit gates, parallel branches with sync points,
  bounded retry/fallback/rollback/safe-stop, human approval checkpoints,
  dynamic re-planning, policy guardrails, and reliability metrics
  (success rate, retry/rollback frequency, MTTR, latency).
- **Scenarios:** `com.agentic.orchestrator.scenarios` — greenfield (add
  custom alias + expiry), brownfield (fix a real click-counter race
  condition), and ambiguous ("make it more secure", normalized behind a
  human approval gate) — all driving real changes to the product
  codebase.

## Prerequisites

- JDK 21 (check with `java --version`)
- Maven 3.8+ (check with `mvn --version`; Maven must be on `PATH` —
  the orchestrator's scenario tests shell out to `mvn`)
- No Docker, no external services, no API keys — everything runs locally
  against a SQLite file.

## 1. Install

From the root of this folder:

```bash
mvn -q -DskipTests package
```

This builds both modules. The orchestrator CLI is packaged as
`orchestrator/target/orchestrator-cli.jar` (fat jar via the shade
plugin).

## 2. Run the test suite

```bash
mvn test
```

The Java port ships no test sources in the repo itself: scenario test
classes (`AliasAndExpiryTest`, `ConcurrentClicksTest`,
`SecurityHardeningTest`) are generated by the scenario implementations
into each disposable workspace, where `RunMavenTestsExecutor` runs them
with `mvn -B test -pl urlshortener -Dtest=<TestClass>` against the
target-dir copy (which is why Maven must be on `PATH`).

Note on the concurrency test: the Python original carries a strict
`xfail` marker on the click-counter race; the Java port marks
`ConcurrentClicksTest` with `@Disabled` instead — the brownfield
scenario removes the marker on a disposable copy of the code as a live
demonstration. It is expected to stay `@Disabled`, not pass.

## 3. Run the URL shortener API

```bash
mvn spring-boot:run -pl urlshortener
```

The server listens on port `8000` (`server.port=8000` in
`urlshortener/src/main/resources/application.properties`).

Then, in another terminal:

```bash
curl -sS -X POST http://localhost:8000/api/urls \
  -H 'content-type: application/json' \
  -d '{"url":"https://example.com"}'
# -> {"code": "aB3xY9z", "short_url": "http://localhost:8000/aB3xY9z", ...}

curl -i http://localhost:8000/aB3xY9z            # redirects (302) to the target
curl http://localhost:8000/api/urls/aB3xY9z/analytics
curl -sS -X DELETE http://localhost:8000/api/urls/aB3xY9z
```

Stop the server with `Ctrl+C`.

## 4. Run an orchestrator scenario

Each scenario's `implementation`/`documentation` stages write **real
files**, so every run must point `--target-dir` at a disposable workspace
copy of the source — **never at this folder's own checkout**. The copy
contains the `urlshortener` module plus the parent `pom.xml` (this is
exactly what `ScenarioCommon.copyUrlShortenerSource` produces, and what
the `mvn` subprocess inside each run needs). Make it with:

```bash
mkdir -p /tmp/greenfield-demo
cp -r urlshortener /tmp/greenfield-demo/
cp pom.xml /tmp/greenfield-demo/
```

Then run the CLI jar:

```bash
java -jar orchestrator/target/orchestrator-cli.jar run greenfield --run-id greenfield-demo --target-dir /tmp/greenfield-demo
java -jar orchestrator/target/orchestrator-cli.jar status greenfield-demo
java -jar orchestrator/target/orchestrator-cli.jar approve greenfield-demo release_readiness --note "ship it"
java -jar orchestrator/target/orchestrator-cli.jar metrics --run greenfield-demo
```

**Brownfield** (fixes the seeded click-counter race with a real
codebase-impact scan):

```bash
mkdir -p /tmp/brownfield-demo
cp -r urlshortener /tmp/brownfield-demo/
cp pom.xml /tmp/brownfield-demo/
java -jar orchestrator/target/orchestrator-cli.jar run brownfield --run-id brownfield-demo --target-dir /tmp/brownfield-demo
java -jar orchestrator/target/orchestrator-cli.jar status brownfield-demo
java -jar orchestrator/target/orchestrator-cli.jar approve brownfield-demo release_readiness --note "atomic fix verified"
```

**Ambiguous** (normalizes "make it more secure" behind a mandatory
approval gate — pauses at `requirements` before anything else runs):

```bash
mkdir -p /tmp/ambiguous-demo
cp -r urlshortener /tmp/ambiguous-demo/
cp pom.xml /tmp/ambiguous-demo/
java -jar orchestrator/target/orchestrator-cli.jar run ambiguous --run-id ambiguous-demo --target-dir /tmp/ambiguous-demo
java -jar orchestrator/target/orchestrator-cli.jar status ambiguous-demo            # requirements: awaiting_approval
java -jar orchestrator/target/orchestrator-cli.jar approve ambiguous-demo requirements --note "scope approved"
java -jar orchestrator/target/orchestrator-cli.jar status ambiguous-demo            # design/implementation/... now ran
java -jar orchestrator/target/orchestrator-cli.jar approve ambiguous-demo release_readiness --note "ship it"
```

Every CLI command prints the current status of each stage in the DAG.
`java -jar orchestrator/target/orchestrator-cli.jar --help` (and
`<command> --help`) lists every subcommand: `run`, `status`, `approve`,
`reject`, `resume`, `stop`, `metrics`.

Demo flow summary (greenfield): copy a disposable workspace as shown
above, run it, approve `release_readiness`. The scenario rewrites real
files under `/tmp/greenfield-demo` only — the repo checkout is never
touched.
